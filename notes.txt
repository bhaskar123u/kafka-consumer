fetch.max.bytes(maximum data for the ENTIRE fetchResponse, limiting factor), max.partition.fetch.bytes(maximum data from EACH individual partition) and max.poll.records are used to control how much data a consumer wants from broker and how much data poll() returns to the application. Kafka can exceed fetch.max.bytes in some cases to return the first batch so the consumer can make progress. Assume fetch.max.bytes = 5 MB && max.partition.fetch.bytes = 10 MB, then

            FetchResponse
            ┌───────────────────────────────┐
            │ Partition 1 → 2 MB(20 records)│
            │ Partition 2 → 1.5MB(15)       │
            │ Partition 3 → 1.5MB(12)       │
            │                               │
            │ TOTAL      → 5 MB(47)         │
            └───────────────────────────────┘
Suppose: max.poll.records = 10. Then the poll() call would return at most 10 records to the application, even though the FetchResponse contains 47 records. The remaining records stay buffered inside the consumer and are returned by subsequent poll() calls.

If you want multiple event types in one topic, you generally use one listener capable of handling the different types, with type information (or another routing mechanism) to determine the concrete object. We might configure like :
spring.kafka.consumer.properties.spring.json.type.mapping= OrderCreated:com.example.events.OrderCreated,PaymentCompleted:com.example.events.PaymentCompleted
and then the application code decides what will happen with this object.

@KafkaListener(topics = "order-events")
public void consume(Object event) {
    if (event instanceof OrderCreated order) {
        // OrderCreated business logic
    }
    else if (event instanceof PaymentCompleted payment) {
        // PaymentCompleted business logic
    }
    else if (event instanceof OrderCancelled cancelled) {
        // OrderCancelled business logic
    }
}

max.poll.interval.ms && session.timeout.ms :
max.poll.interval.ms → maximum allowed time between poll() calls before the consumer is considered to have failed its group membership
session.timeout.ms → if heartbeats aren't received within this period, the Coordinator considers the consumer dead.

During records processing if kafkaConsumer thread is busy and max.poll.interval.ms() expires, then the consumer is considered busy/failed and a re-balance is triggered
                Consumer failure / join / leave
                          ↓

                          ↓
                      Rebalance
                          ↓
                Group Leader calculates assignment
                          ↓
                Consumers receive new partitions
                          ↓
                Consumers find their committed offsets
                          ↓
                Resume consuming

Now if any exception happens, it log it, if configured it will store the result in DLT(dead-letter-topic) and then will commit the offset. In prod env, we need to explicitly add the event in a DLT(it's not done by default) and do a retry. If we only configure the retry it will try all the attempts, if not succeeded, in the end it will log and commit the offset. If we want some database operation/add to DLT or anything like that, we need to configure a Recoverer. We can use the functional interface - ConsumerRecordRecoverer.

How does a message goes into DLT?
When a deserialization exception happens, ErrorHandlingDeserializer catches the exception thrown by the delegate deserializer and internally creates a DeserializationException object containing details about the exception and the failed key/value. It then creates/returns a ConsumerRecord where the failed key or value is represented appropriately, and the DeserializationException information is stored in the record headers along with the raw bytes that caused the failure. This record is then passed through Spring Kafka's error-handling flow to the configured DefaultErrorHandler. The DefaultErrorHandler applies the configured retry policy. For example, with:

            new FixedBackOff(1000L, 2)

the failed record is retried 2 times, with a 1-second interval between attempts. If all retries are exhausted, the DefaultErrorHandler invokes the configured DeadLetterPublishingRecoverer. The DeadLetterPublishingRecoverer then publishes the failed ConsumerRecord to a dead-

Issue with DeadLetterPublishingRecoverer :
Assume the key deserialisation failed then value will be an object(assume order), if the key passed and value failed then value will be still a byte array. Now when writing in -dlt topic, it would need serializer, it can be either of JsonSerializer of byteArraySerializer at a time but not both right? How can we make sure proper serialisation happens?
That's why Spring Kafka supports configuring multiple KafkaTemplates for DeadLetterPublishingRecoverer, with the recoverer selecting the appropriate template based on the value type. For example:

            Map<Class<?>, KafkaTemplate<?, ?>> templates = new LinkedHashMap<>();

            templates.put(Order.class, orderKafkaTemplate);
            templates.put(byte[].class, byteArrayKafkaTemplate);

            return new DeadLetterPublishingRecoverer(templates);

In the both-failed case, neither side is an Order or String anymore. Both are raw bytes:

            key   → byte[]
            value → byte[]

So the DLT producer can use:
ByteArraySerializer
       │
       ├── key   byte[] → bytes
       └── value byte[] → bytes

public DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer recoverer) {

What is exception happens while processing a record?
A processing exception occurs when a Kafka record has been successfully fetched from the broker and successfully deserialized, but an exception occurs while the @KafkaListener method or the business logic invoked by it is executing. At this point, the listener has already received a valid Java object such as Order. For example, if consume(Order order) calls paymentProcessorService.process(order) and that method throws a RuntimeException, the exception is propagated back to the Spring Kafka listener container. The listener container catches the exception and passes it to the configured DefaultErrorHandler. The flow is:
            Kafka Broker
            ↓
            KafkaConsumer.poll()
            ↓
            ConsumerRecord
            ↓
            Deserialization
            ↓
            Order object
            ↓
            @KafkaListener
            ↓
            Business Logic
            ↓
            ❌ Exception
            ↓
            Listener Container
            ↓
            DefaultErrorHandler

Unlike a deserialization exception, the listener method is invoked in this case because deserialization was successful. Therefore, the ConsumerRecord already contains the successfully deserialized key and value. For example, it may contain String as the key and Order as the value. The DefaultErrorHandler is responsible for deciding what to do with the failed record. In our configuration, we have:

            new DefaultErrorHandler(recoverer,new FixedBackOff(1000L, 2));

FixedBackOff(1000L, 2) means that Spring waits for 1 second between retries and performs 2 retries after the initial failed processing attempt. Therefore, the same record can be processed a maximum of 3 times: the initial attempt, retry #1, and retry #2. If the record continues to fail after all retries are exhausted, the DefaultErrorHandler invokes the configured DeadLetterPublishingRecoverer. The recoverer publishes the failed record to the configured Dead Letter Topic (DLT), for example order-events-dlt.

            Initial processing
            ↓
            FAIL
            ↓
            wait 1 sec
            ↓
            Retry #1
            ↓
            FAIL
            ↓
            wait 1 sec
            ↓
            Retry #2
            ↓
            FAIL
            ↓
            DefaultErrorHandler
            ↓
            DeadLetterPublishingRecoverer
            ↓
            order-events-dlt

The important difference between the two failure scenarios is that a deserialization exception occurs before the listener is invoked, whereas a processing exception occurs after the listener has received the successfully deserialized object. In the processing-exception case, if the record is eventually recovered and sent to the DLT, the failed record is handled by the DeadLetterPublishingRecoverer. Once the record has been successfully recovered, the error handler can consider the failed record handled, allowing the consumer to move forward and process subsequent records according to the configured acknowledgment and offset-commit behavior.
